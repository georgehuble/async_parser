# Spec-Driven Development (SDD)

SDD — это подход к разработке, при котором сначала формально описывают, что
система должна делать (specification), а уже потом пишут код. Спецификация
становится единственным источником правды: реализация обязана ей соответствовать.

## Принципы

1. **Спецификация раньше кода.** Любое изменение поведения начинается с изменения
   спецификации. Если спецификация не изменилась — код не должен меняться.
2. **Язык предметной области.** Спецификации пишутся на языке проекта
   (см. `GLOSSARY.md`), понятном и разработчику, и заказчику.
3. **Примеры важнее абстракций.** Сценарии `Given-When-Then` и конкретные примеры
   описывают поведение точнее, чем общие слова (Specification by Example).
4. **Проверяемость.** Каждая спецификация должна быть проверяемой: по ней можно
   написать тесты, а по тестам — убедиться, что код соответствует спецификации.
5. **Одна спецификация — одна ответственность.** Крупные изменения разбиваются
   на несколько небольших спецификаций (SRP).
6. **Сначала контракт, потом реализация.** Интерфейсы (ABC-классы в
   `src/domain/interfaces/`) описываются как контракты: предусловия, постусловия,
   инварианты.

## Что должно быть в спецификации

- Идентификатор, статус, автор и дата.
- Проблема/контекст: зачем это нужно.
- Требования: функциональные и нефункциональные.
- Сценарии поведения в формате Given-When-Then.
- Граничные случаи и обработка ошибок.
- Критерии приёмки.
- Ссылки на связанные ADR, задачи и другие спецификации.

## Жизненный цикл спецификации

| Статус        | Что означает                                           |
| ------------- | ------------------------------------------------------ |
| `draft`       | Черновик. Реализовывать нельзя.                        |
| `review`      | Вынесена на ревью. Учитываются замечания.              |
| `approved`    | Утверждена. На её основе создаются задачи в `TODO.md`. |
| `implemented` | Код написан, тесты проходят, спецификация актуальна.   |
| `done`        | Критерии приёмки подтверждены на практике.             |

## Definition of Done для спецификации

- [ ] Проблема и цель описаны так, что понятны без чтения кода.
- [ ] Сценарии Given-When-Then покрывают основной, альтернативный и ошибочный
      потоки.
- [ ] Граничные случаи описаны.
- [ ] Указаны предусловия и постусловия.
- [ ] Терминология соответствует `GLOSSARY.md`.
- [ ] Пройдено ревью (статус `approved`).

## Как работать

1. Выбрал задачу из `TODO.md` → проверь, есть ли спецификация в `specs/`.
2. Нет спецификации → создай черновик по шаблону `TEMPLATES/FEATURE.md`.
3. Согласуй → статус `approved` → добавь задачи в `TODO.md`.
4. Реализуй, ориентируясь на спецификацию, привяжи код к ID спецификации
   в docstring или комментариях.
5. Обнови статус спецификации после реализации и подтверждения критериев приёмки.
