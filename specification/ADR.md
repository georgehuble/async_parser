# Журнал архитектурных решений (ADR)

Архитектурные решения фиксируются по схеме: контекст -> решение -> последствия.
Статус: `proposed`, `accepted`, `superseded`.

## Шаблон новой записи

```markdown
### ADR-00XX: <короткое название>

- **Статус:** proposed | accepted | superseded
- **Дата:** ГГГГ-ММ-ДД

**Контекст.** ...

**Решение.** ...

**Последствия.** Плюсы: ... Минусы/риски: ...
```

## Принятые решения

### ADR-0001: Разделение Fetch и Parser (SRP)

- **Статус:** accepted

**Контекст.** Один класс отправлял HTTP-запросы и разбирал HTML, что нарушало SRP
и мешало переиспользованию логики разбора.

**Решение.** `Fetch` отвечает за сеть и пагинацию, `Parser` — только за разбор
HTML. `Fetch` получает `Parser` через конструктор (DIP).

**Последствия.** Плюсы: парсер тестируется без сети, каждый класс мал и понятен.
Минусы: на одну страницу приходится два объекта, чуть больше кода связки.

### ADR-0002: Справочник бирж — отдельной таблицей (3НФ)

- **Статус:** accepted

**Контекст.** Название биржи хранилось в каждой записи `trades`, что приводило
к аномалиям обновления при переименовании (нарушение 3НФ).

**Решение.** Таблица `exchanges`; `trades.exchange_id` ссылается на неё по FK.
Обновление названия биржи — это одно обновление в справочнике.

**Последствия.** Плюсы: нет аномалий обновления. Минусы: нужен join/кэш для
получения имени биржи.

### ADR-0003: Бизнес-ключи вместо автоинкремента

- **Статус:** accepted

**Контекст.** `trade_id` (автоинкремент) не подходит для идемпотентной
идентификации записей SPIMEX при повторных запусках парсера.

**Решение.** Бюллетени идентифицируются по `(exchange_id, url)`, сделки — по
`(exchange_id, exchange_trade_id)`. Upsert-логика в `TradeRepository`
(`add_url`, `add`, обновление `file_path`).

**Последствия.** Плюсы: повторные запуски не создают дубликатов. Минусы:
суррогатный `trade_id` остаётся техническим ключом и не участвует
в бизнес-логике.

### ADR-0004: Удаление слоя sources

- **Статус:** accepted

**Контекст.** Слой `sources` дублировал логику работы с биржей, которая уже
есть в downloader и parser.

**Решение.** `sources` удалён; `Orchestrator` работает напрямую с абстракциями
`Downloader` и `Fetch`.

**Последствия.** Меньше кода и связей. Минусы: специфика биржи распределена
по application-слою.

### ADR-0005: StopReason как Enum

- **Статус:** accepted

**Контекст.** Причина остановки пагинации была строковым литералом
(`"cutoff"`, `"max_date"`), что провоцировало опечатки.

**Решение.** `StopReason(Enum)` с вариантами `CONTINUE`, `CUTOFF`, `MAX_DATE`.

**Последствия.** Плюсы: опечатки исключены, код самодокументирован. Минусы:
строковые значения сохранились для логирования.

### ADR-0006: Хранение уже обработанных документов

- **Статус:** accepted

**Контекст.** Повторные запуски парсера скачивали и разбирали одни и те же файлы.

**Решение.** Ссылки хранятся в `trades` с `file_path`; `url_exists`,
`update_file_path_by_url` и флаг `--clear` (очистка всех таблиц) позволяют
пропускать обработанные документы или перезапускать парсинг с нуля.

**Последствия.** Повторный запуск быстрее и не создаёт дубликатов. Минусы:
нужна осторожность с очисткой таблиц.
