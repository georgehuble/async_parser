## Контекст и проблема

Сейчас `Orchestrator` выполняет пайплайн последовательно: сначала парсинг
всех ссылок, затем скачивание всех файлов. Это значит, что:

- на этапе парсинга ничего не скачивается и наоборот — этапы не пересекаются;
- этапы (сбор ссылок, скачивание, разбор файлов) нельзя масштабировать и
  переиспользовать независимо;
- задача из `TODO.md` («модель Pub/Sub») остаётся не закрытой.

## Цель

Разбить пайплайн на независимые шаги, соединённые через `asyncio.Queue`:
ссылки -> файлы -> записи в БД. Шаги работают конкурентно в одном процессе.

## Требования

### Функциональные

- [ ] FR-1: `Producer` собирает ссылки на бюллетени (`Fetch`) и кладёт их
      в очередь `links_queue`.
- [ ] FR-2: `FileConsumer` читает ссылки, скачивает файлы (`Downloader`)
      и кладёт пути файлов в очередь `files_queue`.
- [ ] FR-3: `ParseConsumer` читает пути файлов, разбирает XLS/PDF и сохраняет
      сделки через `TradeRepository`.
- [ ] FR-4: Очереди ограничены по размеру (backpressure), каждый шаг —
      отдельная корутина, запущенная через `asyncio.Task`.
- [ ] FR-5: Корректное завершение: после пустых очередей все корутины
      завершаются без зависаний.

### Нефункциональные

- [ ] NFR-1: Этапы не блокируют друг друга (конкурентное выполнение).
- [ ] NFR-2: Число одновременных HTTP-запросов ограничено (не больше
      `limit_per_host`, см. `SpimexFetch.BATCH_SIZE`).

## Сценарии (Given-When-Then)

| ID   | Given                            | When                     | Then                                  |
| ---- | -------------------------------- | ------------------------ | ------------------------------------- |
| SC-1 | очередь пуста, producer завершён | consumer вызывает `get()`| задача завершается без исключения     |
| SC-2 | ссылка на бюллетень получена     | скачивание файла успешно | путь файла попадает в `files_queue`   |
| SC-3 | файл скачан, БД пуста            | `ParseConsumer` разбирает| сделки сохранены, `file_path` обновлён|
| SC-4 | очередь переполнена              | producer кладёт элемент  | producer ждёт освобождения места      |

## Граничные случаи и ошибки

| Случай                | Поведение системы                                       |
| --------------------- | ------------------------------------------------------- |
| Пустой список ссылок  | producer завершается, consumers корректно останавливаются|
| Сбой скачивания файла | ошибка логируется, ссылка не попадает в `files_queue`, пайплайн продолжается |
| Сбой разбора файла    | ошибка логируется, пайплайн продолжается                |
| Отмена задачи         | очереди закрываются, ожидающие consumers получают `None`|

## Критерии приёмки

- [ ] AC-1: При 10 ссылках и 3 consumers все файлы скачаны, все сделки
      сохранены, дубликатов в БД нет (бизнес-ключи `(exchange_id, url)`).
- [ ] AC-2: При пустом входе приложение завершается без ошибок и зависаний.
- [ ] AC-3: Повторный запуск не скачивает файлы, уже имеющие `file_path`.

## Открытые вопросы

- [ ] Ограничивать ли размер `files_queue` отдельно от `links_queue`.
- [ ] Нужен ли таймаут на ожидание элементов в очереди.
